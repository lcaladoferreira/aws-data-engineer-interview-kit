# DSA Notes for Data Engineers

Complexity and selection notes.

<!-- item -->
## 1. **Question:** How would you explain **arrays** in data engineering interviews?

**Answer:** Define the concept first, state its trade-offs, then connect it to an observable production decision. For arrays, document the input contract, expected scale, failure behavior, and recovery procedure. In data engineering interviews, confirm the decision with a small reproducible test and retain the evidence an interviewer can inspect.

## 2. **Question:** When would you choose **hash tables** in data engineering interviews?

**Answer:** Choose it when its access pattern and operational constraints match the workload; reject it when a simpler design meets the SLO. For hash tables, document the input contract, expected scale, failure behavior, and recovery procedure. In data engineering interviews, confirm the decision with a small reproducible test and retain the evidence an interviewer can inspect.

## 3. **Question:** How would you troubleshoot **stacks** in data engineering interviews?

**Answer:** Start with symptoms and metrics, isolate the failing boundary, validate data and configuration, then change one variable and verify recovery. For stacks, document the input contract, expected scale, failure behavior, and recovery procedure. In data engineering interviews, confirm the decision with a small reproducible test and retain the evidence an interviewer can inspect.

## 4. **Question:** What is the main risk of **queues** in data engineering interviews?

**Answer:** The main risk is treating a context-dependent technique as a default. Control it with explicit assumptions, tests, monitoring, and a rollback path. For queues, document the input contract, expected scale, failure behavior, and recovery procedure. In data engineering interviews, confirm the decision with a small reproducible test and retain the evidence an interviewer can inspect.

## 5. **Question:** How would you optimize **heaps** in data engineering interviews?

**Answer:** Measure the baseline, identify the dominant cost, apply the narrowest effective change, and compare latency, correctness, and cost after the change. For heaps, document the input contract, expected scale, failure behavior, and recovery procedure. In data engineering interviews, confirm the decision with a small reproducible test and retain the evidence an interviewer can inspect.
